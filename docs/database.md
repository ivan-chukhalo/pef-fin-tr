# Схема бази даних (PostgreSQL у Supabase)

Загальні правила:
- Гроші зберігаються в **копійках** (цілі числа).
- Кожна таблиця має `user_id`, на кожній увімкнено Row Level Security (доступ лише власнику).
- Ідентифікатори — UUID.
- Дати — тип `date`, часові мітки створення і зміни — `timestamptz`.

## Таблиці (MVP)

### accounts (рахунки)
| Поле | Тип | Опис |
|---|---|---|
| id | uuid | первинний ключ |
| user_id | uuid | власник (посилання на auth.users) |
| name | text | назва, наприклад «Картка 1», «Готівка» |
| type | text | `card` або `cash` |
| initial_balance_kop | bigint | початковий баланс у копійках |
| is_hidden | boolean | приховано (за замовчуванням false) |
| created_at | timestamptz | |

Баланс не зберігається. Він рахується з `initial_balance_kop`, `transactions` і `transfers`.

Під час звірки поточного балансу застосунок зчитує узгоджений знімок підтверджених рухів і записує в `initial_balance_kop` фактичний залишок мінус чистий рух рахунку. Заплановані операції впливають на прогноз.

Власник може видалити свій рахунок. Зовнішні ключі блокують видалення, якщо рахунок є в транзакції, на будь-якому боці переказу або в повторюваному шаблоні. Для транзакцій і переказів це правило діє для підтверджених і запланованих записів.

### categories (категорії)
| Поле | Тип | Опис |
|---|---|---|
| id | uuid | первинний ключ |
| user_id | uuid | власник |
| name | text | назва (можна змінювати) |
| color | text | колір мітки у форматі `#RRGGBB`, `null` для нейтральної мітки |
| type | text | `income` або `expense` |
| is_hidden | boolean | приховано (за замовчуванням false) |
| created_at | timestamptz | |

Поля «стандартна» немає. Видалення категорій у MVP не передбачено.

Після MVP видалення доступне для невикористаних категорій. Таблиця `category_history` зберігає `user_id`, ідентифікатор категорії `id` та стан `used` або `deleted`. Стан `used` зберігається після зміни або видалення операції чи шаблону. Стан `deleted` не дає застосунку автоматично створити видалену стандартну категорію повторно. Власник має доступ до читання цих позначок через RLS, а записує їх база.

### transactions (доходи і витрати)
| Поле | Тип | Опис |
|---|---|---|
| id | uuid | первинний ключ |
| user_id | uuid | власник |
| account_id | uuid | посилання на accounts |
| category_id | uuid | посилання на categories |
| type | text | `income` або `expense` |
| date | date | дата операції; у MVP не може бути пізніше сьогодні |
| currency | text | `UAH` або `USD` |
| amount_original_kop | bigint | сума в оригінальній валюті, копійки (або центи) |
| rate | numeric | курс на дату операції (для UAH дорівнює 1) |
| amount_uah_kop | bigint | сума в гривнях, копійки, фіксується при збереженні |
| purchase_name | text | необов’язкова назва доходу або покупки |
| comment | text | необов'язково |
| created_at | timestamptz | |
| updated_at | timestamptz | |

Примітка: для долара `amount_uah_kop` = `amount_original_kop` × `rate`, округлене до копійки при збереженні.

### transfers (перекази)
| Поле | Тип | Опис |
|---|---|---|
| id | uuid | первинний ключ |
| user_id | uuid | власник |
| from_account_id | uuid | посилання на accounts |
| to_account_id | uuid | посилання на accounts |
| date | date | дата переказу; у MVP не може бути пізніше сьогодні |
| amount_uah_kop | bigint | сума в гривнях, копійки |
| comment | text | необов'язково |
| created_at | timestamptz | |
| updated_at | timestamptz | версія запису для синхронізації редагування та видалення |

Перевірка: `from_account_id` і `to_account_id` мають бути різними.

## Зміни для версії 1.1

### Нові поля в transactions і transfers
| Поле | Тип | Опис |
|---|---|---|
| status | text | `planned` (заплановано) або `confirmed` (підтверджено). Для існуючих записів — `confirmed` |
| template_id | uuid, може бути порожнім | у `transactions` зв’язує операцію з шаблоном `recurring_templates` |
| occurrence_number | integer, може бути порожнім | порядковий номер операції в шаблоні. Унікальний у межах шаблону |

Дата нового разового плану або перенесення на іншу дату має бути пізнішою за сьогодні за київським часом. Наявний план зберігає свою дату, поки його не перенесуть. Дати операцій із повторюваного шаблону визначає розклад. Для `confirmed` дата має бути не пізніше сьогодні за київським часом. Фактичні баланси й підсумки враховують тільки `confirmed`.

Власник може редагувати й видаляти власні перекази зі статусом `planned`. Перед синхронізацією застосунок звіряє версію `updated_at`, щоб зміна з іншого пристрою збереглася.

### Нова таблиця recurring_templates (шаблони повторюваних операцій)
| Поле | Тип | Опис |
|---|---|---|
| id | uuid | первинний ключ |
| user_id | uuid | власник |
| type | text | `income` або `expense` |
| account_id | uuid | посилання на accounts |
| category_id | uuid | посилання на categories |
| currency | text | `UAH` або `USD` |
| amount_original_kop | bigint | сума за одне повторення |
| rate | numeric | курс для планових операцій |
| purchase_name | text | необов’язкова назва доходу або покупки, яку отримують операції з шаблону |
| comment | text | необов'язково |
| frequency | text | `weekly`, `monthly`, `every_two_months`, `quarterly`, `semiannual` або `yearly` |
| start_date | date | дата першого повторення, від якої рахуються всі інтервали |
| occurrences | integer | скільки разів повторювати (від 1 до 120) |
| created_at | timestamptz | |

Правила:
- Створення шаблону одразу створює `occurrences` записів у `transactions` зі статусом `planned` і `template_id`.
- Інтервал становить тиждень або 1, 2, 3, 6 чи 12 місяців. Якщо в місяці немає потрібного дня (наприклад, 31-го), операція припадає на останній день місяця. Кожна дата рахується від першої, тому після короткого місяця число відновлюється, коли воно є в календарі.
- Зміна шаблону оновлює лише записи зі статусом `planned`. Підтверджені записи не змінюються.
- Видалення шаблону видаляє лише `planned` записи. Підтверджені лишаються в історії, а `template_id` у них обнуляється.
- Підтвердження: статус стає `confirmed`, можна змінити суму і курс.

Відкрите питання: регулярні перекази в 1.1 не передбачені (лише одноразові майбутні перекази).

## Підкатегорії

Таблиця `subcategories` зберігає лише підкатегорії, створені власником. У кожного рядка є `user_id`, `category_id`, `category_type`, назва та ознака приховування. Зв’язок із батьківською категорією перевіряє власника й тип. Політика RLS обмежує доступ власником.

У `transactions` і `recurring_templates` поле `subcategory_id` обов’язкове. Системне значення «Без підкатегорії» зберігається як нульовий UUID без окремого рядка в `subcategories`. Для іншого UUID база перевіряє, що підкатегорія належить тій самій категорії, типу та власнику. Заплановані операції, створені з шаблону, успадковують його підкатегорію.

Підкатегорії входять до резервних копій і локального знімка PWA. Під час відновлення копії без цього поля транзакції й шаблони отримують системне значення. CSV зіставляє підкатегорію за назвою всередині категорії.

## Місячні ліміти за категоріями

Таблиця `category_budget_limits` зберігає зміни ліміту за власником і категорією витрат. Поле `effective_month` містить перший день місяця, з якого діє зміна, а `amount_kop` — додатну суму в копійках. Значення `null` вимикає ліміт із цього місяця. Для звіту береться остання зміна, що вже діяла у вибраному місяці. Факт розраховується з підтверджених витрат в гривнях за цей місяць.

Підтвердження плану записує вибрані суми поточного місяця одним запитом. Унікальна пара категорії й місяця в обліковому записі захищає збережені суми при повторному підтвердженні. Записи за поточний місяць позначають план як підтверджений для нагадування на головній.

Ліміти входять до резервних копій і локального знімка даних PWA. Копії попередніх версій можна відновлювати як стан до появи лімітів.

## Історія відновлень

Таблиця `backup_versions` зберігає ідентифікатор власника, ідентифікатор запиту, дату створення й знімок JSON. Доступ до історії перевіряється за поточною сесією. Підтверджене відновлення з файлу або з історії зберігає попередній стан і замінює дані власника в одній транзакції. Повтор із тим самим ідентифікатором запиту повертає результат без нової заміни.

Версія доступна 30 днів від створення знімка. Прострочені версії видаляються, коли власник відкриває історію або запускає відновлення.

## Зв'язки
- accounts 1 → багато transactions
- categories 1 → багато transactions
- categories 1 → багато subcategories
- subcategories 1 → багато transactions і recurring_templates
- categories 1 → багато category_budget_limits
- accounts 1 → багато transfers (як джерело, `from_account_id`)
- accounts 1 → багато transfers (як отримувач, `to_account_id`)
- recurring_templates 1 → багато transactions (версія 1.1)
- auth.users 1 → багато рядків у кожній таблиці через `user_id`

## Формула балансу рахунку (MVP)
```
баланс = initial_balance_kop
       + сума доходів на рахунку
       − сума витрат на рахунку
       + сума переказів, де рахунок — отримувач
       − сума переказів, де рахунок — джерело
```

## Формула прогнозу на дату X (версія 1.1)
```
прогноз на X = баланс на сьогодні (тільки підтверджені операції)
             + заплановані доходи з датою в (сьогодні, X]
             − заплановані витрати з датою в (сьогодні, X]
             ± заплановані перекази з датою в (сьогодні, X]
             + прострочені заплановані операції (дата ≤ сьогодні, статус planned)
```
Прострочені операції враховуються в прогнозі, доки їх не підтвердять або не видалять. Операції з датою раніше сьогодні виводяться окремо. Заплановані на сьогодні показано в списку за період із позначкою «Прострочено».

## Зміни схеми
Кожна зміна — окрема міграція в Supabase з коротким описом. Ручні зміни в інтерфейсі без запису в міграцію не робимо.
